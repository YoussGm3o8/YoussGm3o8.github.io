01 / The problem

One aircraft can have many software clients. It should not have many competing command owners.

NOMAD is being refactored around a reusable C++ control core so operator interfaces, ROS 2 adapters, perception tools, and competition-specific integrations can share one validated vehicle boundary instead of each owning its own flight-control path.

ArduPilot remains responsible for stabilization, EKF, low-level navigation, motor control, and failsafes. NOMAD sits above that layer: high-level mission behavior, command validation, telemetry state, safety policy, and outcome tracking.

02 / Architecture

Dependencies point inward.

Clients submit typed requests or validated observations. The reusable core owns high-level behavior; MAVSDK/MAVLink is the vehicle transport boundary.

03 / What exists today

A migration in progress, not a finished-product claim.

The public repository explicitly separates implemented pieces from qualification gates and planned competition work.

✓

Working core

Tested C++ core, UDP MAVLink implementation, basic Copter operations, command primitives, safety/watchdog/fence/payload building blocks, and client adapters.

✓

MAVSDK cutover direction

The pinned MAVSDK fork is the production transport direction for ArduPilot semantics, with NOMAD retaining validation, safety policy, deadlines, and outcome authority.

→

→

04 / My contribution

Refactoring the ground-control stack around clearer ownership boundaries.

  • C++ core: refactoring the ground-control system toward a modern C++ control engine that supports multi-platform autonomous missions and live telemetry.
  • MAVSDK fork: maintaining custom ArduPilot command and telemetry behavior required by the project.
  • Long-range networking: integrating non-line-of-sight communication workflows over LTE/Tailscale without treating VPN reachability as a substitute for vehicle safety policy.
  • System integration: connecting ArduPilot, Mission Planner, ROS 2, companion-compute/perception work, and deployment tooling around explicit interfaces.

05 / Engineering decisions

Keep the core reusable. Put event-specific behavior at the edge.

01

One active writer

Multiple clients may observe, but incompatible vehicle requests are serialized or rejected around one command owner.

02

ArduPilot owns flight control

NOMAD supervises high-level behavior rather than reimplementing stabilization, EKF, or low-level flight transitions.

03

Competition logic stays modular

AEAC-specific protocol and scoring behavior live in an optional application module, not in generic vehicle types.

04

Observations ≠ commands

Perception and external systems provide validated observations; they do not directly steer the vehicle around the core.
